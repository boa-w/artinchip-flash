# 更新机制

本工具的检查更新功能基于 GitHub Releases，使用主流 `self_update` crate
做 Release 列表查询，不自造轮子。当前为“检查 + 引导下载”阶段，
暂不做静默自替换（原因见下）。

## 通道

| 通道 | 数据源 | 比较方式 |
|---|---|---|
| `stable`（默认） | 非 prerelease 的 `v*` Release，按 semver 取最大 | `v*` > 本地 `CARGO_PKG_VERSION` 即有更新 |
| `nightly` | 浮动 `nightly` Release | 无 semver 可比：仅当本地构建信息缺失（`unknown`）时提示；否则只给出下载页 |

注意：`self_update` 的列表查询会自动跳过 `nightly` 这类非 semver tag，
这是上游行为，不是 bug。

## 用法

```sh
artinchip-flash update                       # stable 通道，文本输出
artinchip-flash update --channel nightly
artinchip-flash update --open                # 有更新时打开浏览器
artinchip-flash update --json                # 脚本用法
echo $?   # 有更新时退出码为 10，无更新为 0，失败为 1
```

GUI：在设置页选择通道，可开“启动时自动检查”（24 小时节流，
时间戳记在 `config.ini` 的 `last_update_check_unix`），也可点“检查更新”立即查，
“打开下载页”直达对应 Release。

## 便携包 vs 系统安装

| 安装形态 | 更新方式 |
|---|---|
| 便携包（`.zip/.tar.gz` 解压即用） | 从下载页取对应系统 archive 覆盖即可 |
| 系统安装（`msi/setup.exe/deb/pkg`，位于 `Program Files`、`/usr/bin`、`/Applications` 等） | **重跑新版安装器**，不要直接替换二进制 |

`update::is_portable_install()` 按可执行路径是否在系统管理目录、
所在目录是否可写来判断，并在 CLI/GUI 输出中明确提示属于哪一种。
全自动替换（含 Windows 占位替换、`Update.exe` 桩、差分包）是后续可选阶段，
需先把便携包改成单二进制布局，见路线图对照表。

## 发版流程（维护者）

1. 改 `Cargo.toml` 版本号，提交并 push 到 `main`。
2. 打 tag 并推送：`git tag -a vX.Y.Z -m '...' && git push origin vX.Y.Z`。
3. CI 自动三系统构建并创建 `make_latest: true` 的版本化 Release，
   资源命名为 `artinchip-flash-<system>.*`。
4. push 到 `main` 的每次提交另行刷新浮动 `nightly` Release（`make_latest: false`）。

## 限流与代理

- 未登录 GitHub API 限额 60 次/小时（按出口 IP 共享，公司 NAT 下易耗尽）；
  设置 `GH_TOKEN`/`GITHUB_TOKEN` 可提到 5000 次/小时，`self_update` 自动读取。
- 尊重系统代理（`HTTPS_PROXY` 等，经 reqwest）。
- 检查失败只记日志/报错，不阻塞烧录主流程；国内网络超时建议重试或手动开下载页。
